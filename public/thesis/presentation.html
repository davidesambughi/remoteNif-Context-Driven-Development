Cap.03 · App Next.js 07 / 28

App Router, server-first

Frontend e backend nella stessa codebase; per default i componenti girano sul server.

01 — Server Components

I dati si leggono al render, direttamente dal database. Niente chiamate API interne, niente useEffect, niente loading manuali.

02 — Client Components

Solo per le foglie interattive (upload, form). "use client" spinto il più in fondo possibile nell’albero.

03 — Layout annidati

La protezione delle route è centralizzata: l’auth guard è scritto una volta sola e ogni pagina figlia lo eredita.

Conseguenza

Impossibile dimenticare la guard aggiungendo una nuova route.

Cap.03 · App Next.js 08 / 28

Server Actions e proxy.ts

Tutte le mutazioni passano da un unico layer (app/actions/). Le API route esistono solo per i servizi esterni che chiamano l’app via HTTP — webhook Stripe, cron Vercel.

proxy.ts (sostituisce middleware.ts in Next.js 16): intercetta ogni richiesta, valida la sessione e applica il routing multilingua, in un unico punto.

Cap.03 · App Next.js 09 / 28

TypeScript strict e shadcn/ui

TypeScript — modalità strict

Gli stati impossibili diventano irrappresentabili (unioni discriminate). Tutte le azioni hanno la stessa forma di ritorno: ActionResult<T>.

Principio

La solidità non dipende dall’attenzione del programmatore, ma dai vincoli del sistema. Il compilatore intercetta gli errori strutturali.

shadcn/ui

I componenti UI sono codice copiato nel repository, non una dipendenza npm. Modificabili, senza version lock-in.

Il brand è applicato tramite design token in CSS.

Cap.04 · Dati & backend 11 / 28

Sicurezza nell’infrastruttura

Row Level Security

Le policy di accesso vivono nel database, non nel codice. Un bug applicativo non può far trapelare dati di altri utenti.

Trigger handle_new_user

Garantisce a livello di DB che ogni utente di Auth abbia la riga corrispondente, qualunque sia il percorso di creazione.

Storage — Signed URL (1h)

L’upload va direttamente dal browser a Supabase, senza passare dal server.

Gerarchia applicativa

getCurrentUser → requireAuth → requireRole. Chi arriva su /admin senza permessi viene rediretto, senza che la route venga confermata.

Cap.05 · Pagamenti & comunicazioni 13 / 28

Stripe

Checkout Sessions: l’utente paga su pagina ospitata da Stripe. I dati della carta non toccano mai l’app (PCI, 3D Secure a carico di Stripe).

Idempotenza a doppio livello: controllo applicativo + vincolo UNIQUE nel database. Un evento duplicato crea un solo ordine.

La conferma del pagamento arriva solo dal webhook, mai dal redirect del browser — raggiungibile anche senza pagare.

WebhookPoller: overlay di attesa dopo il redirect, interroga il DB ogni 2,5s finché l’ordine appare — scelta UX per la race condition.

[ Visual ] Flusso Stripe a 6 fasi — al passo 6 le due frecce (redirect browser vs. webhook POST). Solo il webhook è la conferma valida.
Cap.05 · Pagamenti & comunicazioni 14 / 28

Zod — validazione ai confini

Validazione a runtime dove TypeScript non arriva. Il tipo è inferito dallo stesso schema, non scritto a parte.

I confini form webhook variabili d’ambiente risposta AI
Zod

env.ts — se una variabile manca o ha formato errato, l’app non parte. Fail fast.

L’output del modello AI è trattato come input non fidato: validato con vocabolario chiuso prima di toccare il database.

“never trust LLM output directly”

I file di integrazione girano in sequenza (fileParallelism: false): l’esecuzione parallela causerebbe collisioni sulle foreign key tra file diversi.

Cap.08 · Il metodo — il cuore della tesi 25 / 28

Manutenzione del sistema di contesto

Un agente che lavora su documentazione obsoleta non sa di stare sbagliando: il suo output è coerente con le premesse date.

La soluzione — Audit Sprint

Sessioni dedicate esclusivamente a verificare la corrispondenza tra documentazione e codebase.

10divergenze trovate nell’Audit Sprint 6 — ciascuna categorizzata e risolta in modo tracciabile
Esempio concreto

La documentazione dichiarava polling per 30s sul checkout. Il codice non faceva polling.

La discrepanza è stata documentata e risolta esplicitamente — non silenziosamente.

Cap.09 · Conclusioni 26 / 28

Sviluppi futuri

Non ridurre il rigore architetturale, ma usare la velocità per affrontare problemi più complessi.

Fase 1
Agent Skills

Astrarre i pattern ricorrenti del progetto in set di istruzioni modulari e riutilizzabili, invece di riscrivere prompt ogni volta.

Fase 2
Gestione delle eccezioni

Un workflow standard per come il sistema reagisce, documenta e si riprende dai fallimenti delle chiamate esterne o dalle allucinazioni dell’agente.

Fase 3
Esecuzione asincrona e autonoma

Test e documentazione così solidi da lanciare task complessi in cicli notturni non supervisionati, validati da build e test.

Cap.09 · Conclusioni 27 / 28

Lezioni apprese dall’attrito

Design System predefiniti

Senza mockup rigorosi, l’agente genera interfacce incoerenti e i cicli di riscrittura si moltiplicano.

Context drift

Aggiornare i file di contesto “dopo” porta il modello a lavorare su premesse obsolete. La documentazione deve essere sincrona con il codice.

Testing E2E assente

Unit e integration test proteggono la logica, non i flussi di navigazione. In un ambiente ad alta rigenerazione UI, l’E2E è infrastruttura, non opzione.
